# nyraflow desk

Telegram Mini App студии. Живёт отдельным контейнером на том же сервере, что и
лендинг, за тем же Caddy, на домене `app.nyraflow.ru`.

## Что это

Одно приложение с тремя режимами:

1. **Пресейл** — конфигуратор задачи, вилка сметы из прайса студии, бриф с
   AI-разбором, заявка и бронь созвона.
2. **Кабинет клиента** — проект по пяти этапам процесса студии, блок «нужно от
   вас», согласования дизайн-концепта, счета.
3. **Админ** — лента заявок, перевод этапа, апдейты клиенту.

Всё состояние живёт в Postgres, все значимые действия порождают события в
`outbox_events`, откуда отдельный воркер доставляет их в n8n.

## Статус

Готов фундамент: контейнер, база со схемой на все три режима, авторизация через
Telegram initData, health-эндпоинт. Интерфейс, AI-разбор и доставка событий в
n8n — следующими шагами.

## Архитектура

```
miniapp/
  app/
    api/health/route.ts   живость приложения + доступность базы
    api/me/route.ts       профиль текущего пользователя (сквозная проверка авторизации)
    api/telegram/webhook  апдейты бота: /start, /help и любой другой текст
  lib/
    env.ts                ленивый доступ к переменным окружения
    db/client.ts          пул pg, хелперы query/queryOne/transaction
    db/users.ts           upsert пользователя при входе
    auth/session.ts       авторизация по заголовку `Authorization: tma <initData>`
    telegram/init-data.ts проверка подписи initData
    telegram/bot.ts       отправка сообщений тем же ботом, что и заявки с сайта
    telegram/messages.ts  тексты бота: приветствие, уведомления, разбор команд
  migrations/             SQL-миграции, применяются по возрастанию имени
  scripts/migrate.mjs     раннер миграций (запускается до старта приложения)
  scripts/bot-worker.mjs  входящие апдейты бота: поллинг + настройка команд
```

### Бот

Бот у мини-аппа и лендинга общий, и до сих пор он умел только отправлять:
человек жал «Старт» и не получал ничего. Теперь есть обработчик входящих
(`/api/telegram/webhook`), который отвечает на `/start` приглашением с кнопкой
`web_app`, на `/help` — тремя строчками о том, как всё устроено, а на любой
другой текст — подтверждением, что сообщение дошло. Приветствие зависит от
состояния: новичка зовёт к брифу, автора уже отправленной заявки — к её статусу.

**Апдейты приходят поллингом, а не вебхуком.** Вебхук на этом сервере
невозможен: Telegram не доходит до российского IP — на каждой попытке
`Connection timed out`, до Caddy не долетает ни одного запроса, при том что
снаружи сайт открывается за 0,2 с. Это та же причина, по которой серверу нужен
VPN, чтобы самому писать в `api.telegram.org`. Поэтому апдейты забирает
`scripts/bot-worker.mjs` (контейнер `bot`): long polling через VPN, затем POST
в тот же эндпоинт по внутренней сети. Логика ответов живёт в одном месте, и в
день, когда появится точка входа за границей, воркер выключается, а эндпоинт
остаётся как есть.

Эндпоинт публичный, поэтому защищён общим секретом `TELEGRAM_WEBHOOK_SECRET`
(заголовок `X-Telegram-Bot-Api-Secret-Token`) — его подставляет воркер, а всё
остальное отбрасывается с 403. Пустой секрет проверку выключает.

Команды бота и кнопку меню воркер выставляет сам при каждом старте: настройка
идемпотентна, и отдельный скрипт, который надо не забыть запустить, — лишняя
причина для расхождения.

Когда разбор готов, в чат уходит короткое «бриф принят, разбор готов» с кнопкой.
Сам разбор остаётся в приложении: мини-апп закрывают сразу после отправки, и без
сообщения в переписке не остаётся ни следа заявки, — но девять абзацев разбора в
чате читались бы как рассылка, а на экране у них есть вёрстка, разделы,
состояние заявки и кнопка «обсудить».

Проверить, что бот жив:

```bash
docker compose logs --tail 20 bot
```

### Авторизация

Сессий на сервере нет. Клиент отдаёт `window.Telegram.WebApp.initData` в
заголовке `Authorization: tma <initData>`, сервер проверяет HMAC-подпись ботовым
токеном и свежесть `auth_date`. Пользователь заводится при первом обращении;
роль `admin` выдаётся только тем, чей Telegram id перечислен в
`TELEGRAM_ADMIN_IDS`, и не понижается при повторных входах.

### Миграции

`scripts/migrate.mjs` применяет новые файлы из `migrations/` — каждый в транзакции,
под advisory lock. Запускается в `CMD` контейнера до `node server.js`: если
схема не накатилась, приложение не стартует вовсе.

Новая миграция — новый файл `NNNN_описание.sql`. Существующие файлы не
редактируются: они уже применены на сервере.

## Переменные окружения

Полный список с комментариями — в [.env.example](.env.example). На сервере
лежат в `/opt/myland/.env`, оттуда их читает `docker compose` (тот же файл, что
у лендинга).

## Локальная разработка

Node на машине разработчика не установлен — сборка и запуск идут в Docker на
сервере, как и у лендинга. Если Node появится:

```bash
npm install
npm run migrate
npm run dev
```

Мини-апп поднимется на порту 3001, чтобы не конфликтовать с лендингом.

## Деплой

Тот же цикл, что у лендинга (см. [DEPLOY.md](../DEPLOY.md)):

```bash
rsync -a --exclude node_modules --exclude .next --exclude .git ./ root@SERVER:/opt/myland/
ssh root@SERVER 'cd /opt/myland && docker compose up -d --build'
```

Требуется до первого деплоя:

- `A`-запись `app.nyraflow.ru` → IP сервера;
- `POSTGRES_PASSWORD`, `DATABASE_URL` и `TELEGRAM_ADMIN_IDS` в `/opt/myland/.env`;
- в BotFather у существующего бота — кнопка меню с адресом `https://app.nyraflow.ru`
  (её же выставляет воркер бота при старте);
- `TELEGRAM_WEBHOOK_SECRET` в `/opt/myland/.env` — иначе входящий эндпоинт
  открыт для чужих POST.

Проверка после деплоя:

```bash
curl -s https://app.nyraflow.ru/api/health
```
