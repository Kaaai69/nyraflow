# nyraflow

Экосистема студии: лендинг, Telegram Mini App и автоматизация. Всё живёт в одном
репозитории и на одном сервере, но это три отдельных приложения со своими
сборками — путать их нельзя, и большинство проблем случалось именно там, где
они встречаются.

```
nyraflow.ru          лендинг            Next.js, контейнер app
app.nyraflow.ru      мини-апп «desk»    Next.js + Postgres, контейнер miniapp
n8n.nyraflow.ru      автоматизация      n8n, контейнер n8n
                     доставка событий   контейнер outbox
```

---

## 1. Автоматизация: n8n и сценарии

Начинаем отсюда, потому что это связующий слой: он объясняет, зачем мини-апп
устроен именно так.

### Что такое сценарий

Сценарий в n8n — цепочка шагов, которая запускается событием. Не программа, а
схема: шаги видно целиком, каждый можно поменять отдельно, без пересборки
приложения. Это принципиально: **логика реакции на события живёт вне кода**,
и правится в браузере, а не через деплой.

### Как события попадают в n8n

Мини-апп не вызывает n8n напрямую. Между ними — транзакционный outbox:

```
действие пользователя
   ↓
одна транзакция Postgres: данные + запись в outbox_events
   ↓
воркер (контейнер outbox) забирает пачку, шлёт POST с HMAC-подписью
   ↓
n8n: проверка подписи → ветвление по типу → действие
```

Зачем так, а не прямой вызов:

- **Событие не теряется.** Заявка и событие о ней пишутся одной транзакцией.
  Не бывает заявки, о которой автоматизация не узнала.
- **n8n может лежать.** События копятся в очереди и уезжают, когда он поднимется.
- **Повторы бесплатны.** Воркер сам ретраит с нарастающей задержкой: 10 с, 20 с,
  40 с и далее до часа, максимум 8 попыток, потом статус `dead`.

Код: [`miniapp/scripts/outbox-worker.mjs`](miniapp/scripts/outbox-worker.mjs),
[`miniapp/lib/db/outbox.ts`](miniapp/lib/db/outbox.ts).

### Доставка «хотя бы один раз»

Если n8n принял событие, но не успел ответить, воркер попробует снова — и
сценарий отработает дважды. **Сценарии обязаны быть идемпотентными**: заголовок
`x-nyraflow-event-id` содержит идентификатор, по которому повтор отличается от
нового события.

Адресов может быть несколько через запятую в `N8N_WEBHOOK_URL` — по одному на
сценарий. Событие считается доставленным, когда приняли все; если один отказал,
повтор уйдёт во все, включая уже отработавшие. Это и есть причина требования
идемпотентности.

### Подпись

Тело запроса подписывается HMAC-SHA256 ключом `N8N_WEBHOOK_SECRET`, подпись
идёт в заголовке `x-nyraflow-signature`. Секрет одинаковый у воркера и у n8n.

В сценарии проверка живёт в блоке `Code`. Чтобы он видел переменные окружения,
в compose заданы два флага — без них проверка молча считает **все** события
неподписанными:

```yaml
NODE_FUNCTION_ALLOW_BUILTIN: crypto      # доступ к require('crypto')
N8N_BLOCK_ENV_ACCESS_IN_NODE: "false"    # доступ к $env
```

### Сценарии

Экспорты лежат в [`miniapp/n8n/`](miniapp/n8n/) — это единственная резервная
копия автоматизации. Сами сценарии живут в базе внутри контейнера n8n; **после
правок в интерфейсе экспортируйте их обратно в репозиторий**.

| Файл | Что делает |
|---|---|
| `01-lead-notification.json` | Заявка или разбор → короткое уведомление команде |
| `02-brief-summary.json` | Разбор готов → развёрнутое саммари с оффером |
| `03-followup-reminder.json` | Разбор готов → пауза сутки → если клиент молчит, напомнить |

Третий показателен: `Respond` стоит **до** паузы. Если бы он стоял в конце,
воркер ждал бы 15 секунд, счёл доставку провалившейся и через сутки прислал бы
событие повторно.

### Типы событий

| Событие | Когда |
|---|---|
| `lead.created` | Заявка создана или сменила статус |
| `brief.submitted` | Бриф записан, разбор ещё не готов |
| `brief.analyzed` | Разбор готов: провайдер, модель, формат, выжимка |
| `stage.changed` | Проект перешёл на следующий этап |
| `approval.granted` | Клиент принял или запросил правки |
| `task.overdue` | Задача клиента просрочена или закрыта |
| `invoice.paid` | Счёт оплачен |

В payload есть `telegramId` — чтобы сценарий мог написать клиенту, не обращаясь
за ним в API. Добавлять поля в события безопасно, **переименовывать и удалять —
нет**: сломаются все сценарии разом.

### Входящий API

Обратный путь: n8n читает и меняет состояние через `/api/admin/leads/[id]`,
авторизация — `Authorization: Bearer <ADMIN_API_TOKEN>`.

## 2. Мини-апп: nyraflow desk

Telegram Mini App с тремя режимами в одном приложении. Подробности —
[`miniapp/README.md`](miniapp/README.md), план — [`miniapp/ROADMAP.md`](miniapp/ROADMAP.md).

**Пресейл.** Бриф из восьми вопросов по одному на экран, ответы в localStorage.
AI-разбор задачи: структура сайта, гипотеза оффера, риски, вопросы клиенту.

**Кабинет клиента.** Пять этапов процесса студии, блок «нужно от вас»,
согласования с обязательным комментарием к правкам, счета.

**Админ.** Лента заявок с приоритетом, карточка с брифом и разбором, смена
статуса, создание проекта из заявки одним нажатием.

### Авторизация

Серверных сессий нет. Клиент шлёт `initData` в заголовке
`Authorization: tma <initData>`, сервер проверяет HMAC-подпись ботовым токеном.

**Грабля:** в `initData` современных клиентов есть поле `signature`, и Telegram
считает `hash` **вместе с ним**. Документация нового формата предлагает его
исключать. Проверяются оба варианта — иначе живые пользователи получают
`bad_hash`, а браузер работает нормально (там этого поля нет).

### AI-слой

Провайдер задаётся тройкой переменных, настроен — только если заданы все три.
Ненастроенный слот молча пропускается.

```
AI_PRIMARY   Groq        openai/gpt-oss-20b        ~2 с
AI_FALLBACK  OpenRouter  openai/gpt-oss-20b:free   ~7 с
```

Фолбэк намеренно та же модель: при отказе основного провайдера качество разбора
не меняется.

Порядок: основной → запасной → **разбор по правилам без модели**. Клиент никогда
не видит «AI недоступен»; шаблонный разбор помечается флагом `is_fallback`.

Три вещи, которые стоили отдельных итераций:

- **Ретрай на 429.** Минутный лимит Groq — 6000 токенов, один разбор ест ~3500.
  Два клиента подряд упирались в него штатно.
- **Фильтр тем поверх промпта.** Инструкция задаёт намерение, но модель такого
  размера правила забывает — выдавала бюджет клиента как риск. Запрещённые
  формулировки выбрасываются кодом в [`lib/ai/schema.ts`](miniapp/lib/ai/schema.ts).
- **Контакты вырезаются** из брифа перед отправкой в модель: бесплатные тарифы
  оставляют за собой право учиться на переданных данных.

### Приоритет заявки

Считается из бюджета, срока, формата задачи и отклика клиента; суммы и сроки
разбираются из свободного текста. Логика вынесена в
[`lib/leads/priority.ts`](miniapp/lib/leads/priority.ts) и покрыта тестами —
это самое хрупкое место, клиенты пишут «150к», «до 1.5 млн», «полтора месяца».

## 3. Лендинг

Next.js на `nyraflow.ru`. Контент отделён от вёрстки в
[`content/home.ts`](content/home.ts), секции — в `components/home/`.

Визуальный язык: чёрный фон, Onest, стеклянные карточки `card-glass`, появление
через `MotionGrid` / `MotionCard`. Фон — WebGL-шейдер `BackgroundWaves`; он же
перенесён в мини-апп, чтобы картинка совпадала.

Секция `AutomationSection` показывает автоматизацию студии на её же примере и
ведёт в мини-апп с меткой источника — она приходит в `start_param` и видна в
заявке.

## 4. Инфраструктура

Один сервер, один `docker-compose.yml`, шесть контейнеров. Развёртывание —
[`DEPLOY.md`](DEPLOY.md), работа с сервером — [`docs/runbook/`](docs/runbook/README.md).

| Контейнер | Роль |
|---|---|
| `app` | Лендинг |
| `miniapp` | Мини-апп, миграции применяются до старта |
| `outbox` | Доставка событий в n8n |
| `db` | Postgres 17, наружу не публикуется |
| `n8n` | Автоматизация, своё хранилище |
| `caddy` | HTTPS и маршрутизация доменов |

Весь исходящий трафик сервера идёт через AmneziaWG — так достижимы Telegram и
Groq. Выход в Варшаве; **Gemini с этого адреса недоступен** независимо от страны:
Google блокирует диапазоны хостеров.

### Правила, оплаченные ошибками

**Деплой мини-аппа не синхронизирует лендинг.** `rsync -a ./` на весь каталог
перезаписывает чужие свежие файлы, а сайт продолжает работать на старом образе —
поломка всплывает при следующей сборке. Синхронизируйте по белому списку:
[`docs/runbook/templates/deploy-miniapp.sh`](docs/runbook/templates/deploy-miniapp.sh).

**Caddyfile монтируется по inode.** После `rsync`, подменившего файл, контейнер
продолжает читать старую версию, а `validate` и `reload` рапортуют успех, проверяя
не тот файл. Помогает только `docker compose up -d --force-recreate caddy`.

**`miniapp` исключён из сборки лендинга** в `tsconfig.json` и `.dockerignore`.
Иначе `next build` типизирует чужие файлы с чужими алиасами и падает.

**Не перезапускайте Caddy до создания DNS-записи** — упрётесь в лимит Let's
Encrypt: 5 неудачных проверок в час на домен.

**`\b`, `\w`, `\d` рядом с кириллицей — подозреваемые по умолчанию.** В
JavaScript они определены через `[A-Za-z0-9_]`. Из-за `\b` разбор бюджета молча
возвращал `null`; через час та же ошибка повторилась с `\w` в фильтре тем. Оба
раза поймали тесты, оба раза код выглядел правильным при чтении.

## 5. Работа с проектом

```bash
# тесты мини-аппа (66 проверок)
docker run --rm -v /opt/myland/miniapp:/w -w /w node:24-alpine \
  sh -c "npm install --silent && npx vitest run"

# деплой мини-аппа
rsync -a --exclude node_modules --exclude .next ./miniapp/ root@SERVER:/opt/myland/miniapp/
ssh root@SERVER 'cd /opt/myland && docker compose up -d --build miniapp outbox'

# состояние
ssh root@SERVER 'cd /opt/myland && docker compose ps'
curl -s https://app.nyraflow.ru/api/health
```

Node на машине разработчика не нужен: сборка идёт в Docker на сервере.

**Бэкапы** — ежедневно в 4:17, хранение 14 дней, с проверкой целостности дампа:
[`docs/runbook/templates/pg-backup.sh`](docs/runbook/templates/pg-backup.sh).
Восстановление из дампа пока не проверялось — это открытый пункт.
