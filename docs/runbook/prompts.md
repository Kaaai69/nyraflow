## 1. Развернуть VPN (full-tunnel) на сервере

Приложить: `server.txt` (доступы), `vpn.conf`.

```
Разверни на сервере full-tunnel VPN из приложенного конфига (vpn.conf), чтобы
ВЕСЬ исходящий трафик сервера (хост + Docker-контейнеры) шёл через VPN, но
сервер оставался доступен по SSH и на портах 80/443 по его РЕАЛЬНОМУ IP.

Доступы в server.txt. Если в vpn.conf есть поля Jc/Jmin/Jmax/S1/S2/H1-H4 — это
AmneziaWG, обычный WireGuard его не поймёт.

Действуй так и учти грабли, на которые уже наступали:

1. Определи ОС/ядро. Ставь AmneziaWG. Если в PPA нет пакета под этот дистрибутив
   или нет модуля ядра — собери из исходников userspace-версию amneziawg-go +
   amneziawg-tools (github.com/amnezia-vpn) и включи
   WG_QUICK_USERSPACE_IMPLEMENTATION=amneziawg-go.

2. Конфиг → /etc/amnezia/amneziawg/awg0.conf (права 600).

3. Исключение для входящих (иначе полный туннель рвёт SSH и сайт):
   - connmark --set-mark 0x2 на НОВЫЕ входящие TCP на портах 22,80,443
     с внешнего интерфейса;
   - restore-mark в OUTPUT ТОЛЬКО для connmark 0x2 — иначе затрёшь fwmark
     самого WireGuard на его зашифрованных пакетах и получишь петлю;
   - restore-mark в PREROUTING только для трафика НЕ с внешнего интерфейса
     (! -i eth0) — иначе входящий DNAT-трафик к контейнерам уйдёт не туда
     и сайт перестанет открываться снаружи;
   - пакеты с fwmark 0x2 → отдельная таблица маршрутизации с реальным шлюзом;
   - правило ip rule добавляй ПОСЛЕ подъёма awg-quick с pref 50: awg-quick
     ставит свои правила на 1-2 ниже самого низкого пользовательского;
   - MSS clamping на выход в туннель (--clamp-mss-to-pmtu), MTU ~1380.

4. Оформи systemd-сервисом с Type=oneshot и RemainAfterExit=yes (иначе systemd
   убьёт userspace-демон). Включи автозапуск.

5. КРИТИЧНО — не залочь меня: поднимай туннель отсоединённым процессом плюс
   watchdog, который через ~2 минуты САМ откатит VPN, если я не подтвержу связь.
   Проверяй так: переподключись НОВОЙ SSH-сессией и убедись, что (а) SSH жив,
   (б) внешний IP сменился на VPN-выход, (в) сайт на 80/443 отвечает снаружи.
   Только после этого снимай watchdog и фиксируй автозапуск.

Верни: внешний IP до/после, статус хэндшейка, подтверждение что SSH и веб живы.
```

## 2. Задеплоить лендинг в Docker + Caddy

```
Задеплой этот проект на сервер: Docker + Caddy, автоматический HTTPS.
Доступы в server.txt. Домен: <DOMAIN> (A-запись уже указывает на сервер).

Правила:
- проект в /opt/<PROJECT>, отдельный compose-проект;
- приложение НЕ публикует порты наружу, наружу смотрит только Caddy (80/443),
  приложение доступно ему по имени сервиса во внутренней docker-сети;
- секреты только в /opt/<PROJECT>/.env на сервере (права 600), подключить через
  env_file; в git и в образ они попадать не должны;
- .dockerignore обязан исключать .env*, node_modules, .next, .git и файлы с ключами;
- многоступенчатая сборка, рантайм под non-root пользователем;
- в Dockerfile сделай chmod -R a+rX на public/статику: под non-root файлы с
  правами 600 отдают 500 вместо картинки;
- restart: unless-stopped у всех сервисов;
- для Caddy обязательно том caddy_data, иначе сертификаты будут перевыпускаться;
- для Next.js SSR проверь, что в next.config стоит output: "standalone".

После деплоя проверь СНАРУЖИ (не с сервера) и покажи коды ответов:
главная 200, http→https редирект, www→апекс, валидность сертификата,
ключевые страницы, картинки. Если есть формы — отправь тестовую заявку и
подтверди, что она дошла.
```

## 3. Обновить уже развёрнутый лендинг

```
Обнови задеплоенный лендинг на сервере (доступы в server.txt, проект в
/opt/<PROJECT>).

Скопируй изменения без node_modules/.next/.git/.env*, пересобери только сервис
app (docker compose up -d --build app), Caddy не трогай.

Проверь снаружи, что главная и изменённые страницы отвечают 200, и покажи
результат. Секреты на сервере не перезаписывай.
```

## 4. Диагностика «сайт не открывается»

```
Сайт <DOMAIN> не открывается снаружи. Доступы в server.txt, проект в
/opt/<PROJECT>. Разберись и почини.

Проверь по порядку и покажи результат каждого шага:
1. docker compose ps — контейнеры живы?
2. Локально на сервере: curl -I http://127.0.0.1 — Caddy отвечает?
3. docker compose logs caddy | tail -30 — ошибки TLS/ACME/прокси?
4. docker compose logs app | tail -30 — приложение поднялось, слушает 0.0.0.0?
5. Снаружи: tcpdump -ni eth0 tcp port 80 — SYN доходят? ответы уходят?
6. Если SYN доходят, а ответа нет — почти наверняка порты 80/443 не попали в
   исключения full-tunnel VPN (см. /usr/local/sbin/vpn-exempt.sh, переменная PORTS).
7. dig +short <DOMAIN> — DNS указывает на этот сервер?

Ничего не ломай необратимо: перед изменением правил маршрутизации ставь
watchdog с автооткатом.
```
